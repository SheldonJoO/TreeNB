# TreeNB 启动链改造设计：从"跳转"到"单包无跳转"

> 状态：历史设计草案。2026-11-28 起，guest 返回路径已由“重开同一 bundle、冷启动接管”取代；本文第 2 节与第 3.4 节中“dismiss 回主壳”的描述仅保留为设计演进证据，不代表当前实现。

> 本文是 TreeNB 的核心技术蓝图。目标只有一个：**干掉 openSSS 作为 guest 被启动的那条路径**，
> 让 openSSS 的 Shell 成为 App 启动后的主界面，LiveContainer 的多开能力退居内嵌模块。

---

## 1. "跳转"到底是怎么发生的（现状精确还原）

基于 TreeNewBee 真实代码（`_reference/TreeNewBee/`）：

### 1.1 进程启动链

```
dyld → main.c: LiveContainerMainC()
         └─ dlopen("LiveContainerShared.framework")
         └─ dlsym("LiveContainerMain")   ← LCBootstrap.m
              │
              ├─ 有 selectedApp 或 isSideStore ?
              │    └─ YES → invokeAppMain()          ★ 进程主线权交给 guest
              │              └─ guest 的 UIApplicationMain → 宿主 UI 退后台
              │
              └─ NO → dlopen("LiveContainerSwiftUI.framework")
                     └─ dlsym("main") → LiveContainerSwiftUIMain()
                        └─ LCTabView（三 Tab UI）
```

### 1.2 "跳转"的三个触发点（都要拆）

| # | 触发点 | 文件:行 | 代码 |
|---|---|---|---|
| 1 | openSSS Tab 过场页 | `TreeOpenSSSTabView.swift:66` | `LCUtils.openSideStore()` |
| 2 | openSideStore 实现 | `LCUtilsExtensions.swift:519` | `sideStoreApp.runApp(bundleIdOverride: "builtinSideStore")` |
| 3 | 启动链的 guest 分支 | `LCBootstrap.m:827-833` | `LCOpenSideStore` → `isSideStore = true` → `invokeAppMain()` |

**关键事实**：`openSideStore()` 最终走的是 `runApp()`，它设置 `selected=builtinSideStore` 后重进 `LiveContainerMain`，命中 `LCBootstrap.m:885` 的 `if (selectedApp || isSideStore)`，调用 `invokeAppMain()` 把整个进程交给 openSSS 的 `UIApplicationMain`。宿主 LiveContainer 界面**不是 push/present，是被整个替换**——这就是用户看到的"跳转"。

### 1.3 打包侧的配合（为什么要 dylibify）

`local-build-openSSS.sh:94-112` 把 openSSS 塞进 `SideStoreApp.framework` 并 dylibify，是因为 guest 必须从 framework 里 dlopen 出来跑。**这条链在 TreeNB 里整个删掉**——openSSS 是本体内涵，不需要伪装成 framework。

## 2. 目标架构：反转主从

```
dyld → openSSS 的 @UIApplicationMain（AppDelegate/SceneDelegate）
         └─ openSSS Shell 作为 root（Apps / 定位 / 我的 + 新增"容器"Tab）
              │
              ├─ 签名/续签/Anisette/应用源  ← openSSS 原生引擎（本体内涵）
              ├─ "容器" Tab                 ← LiveContainer 多开 UI（内嵌 View）
              │    └─ 用户点某个 guest App → invokeAppMain()（进程接管，保留）
              │         └─ 悬浮返回键 → dismiss 回 openSSS Shell
              └─ AltWidgetBundle            ← TreeWidget 并入（单一 @main）
```

**核心变化**：
- 主 executable 从 `LiveContainer` 变成 `openSSS`（不再需要 LC 当发动机起头）
- `main.c` / `LCBootstrap.m` 的**入口部分**不再被 dyld 首先命中；LC 引擎作为 framework 被 openSSS 在需要时 dlopen
- guest App 启动时仍走 `invokeAppMain()`（这是 LiveContainer 的本质，无法也不必消除）——但**用户不会"跳到另一个 App"**，因为起点就是 openSSS，切 guest 是 App 内的功能，返回回 App 内

> 澄清一个容易混淆的点："无跳转"指的是**不再从 openSSS 跳到 LiveContainer 再跳回来**。
> guest App 本身的启动（点某个侧载 App 全屏运行）是 LiveContainer 的核心功能，必须保留。
> 区别是：现在这两个能力在同一个 App 里，用户心智模型是"一个 App 里的两个页面"，不是"两个 App 来回跳"。

### 2.1 真实代码核对：主壳能力已就绪（2026-11-23 经 GitHub API 核实）

拉 openSSS 整仓时网络反复中断，改用 GitHub 文件接口精准取了 `AppDelegate.swift`、`ShellTabBarController.swift` 核对，确认三个利好事实：

1. **`@UIApplicationMain` 确实在 openSSS 的 `AppDelegate` 上**——反转主从后它就是主入口，无需新增入口类。
2. **后台续签问题自动消失**：`didFinishLaunchingWithOptions` 里已有 `BackgroundServiceManager.ensureBackgroundServicesStarted()`、`AppBootManager.shared.startBootSequence()`、`BackgroundRefreshTaskScheduler.register()`，还有完整的"续签失败→退避提醒→回前台重试"逻辑（`recordBackgroundRefreshOutcome` / `retryFailedBackgroundRefreshIfNeeded`）。**openSSS 当主进程时这些照常运行**，不存在旧方案里"guest 运行时续签不常驻"的硬伤。原可行性报告 §关键决策那条的顾虑，在新方案下作废。
3. **加"容器"Tab 的成本比预想低**：`ShellTabBarController` 用 `lazy var` 构造三个 `UINavigationController`，`viewControllers = [appsNav, locationNav, profileNav]` 是简单数组赋值——加第四个 Tab 只需新增一个 lazy var + 改这行数组。它还有现成的深链观察者模式（`NotificationCenter` + `importAppDeepLinkNotification` 等），容器 Tab 的深链可直接照搬。
4. **Widget 数据管道已通**：`AppDelegate` 启动时调 `WidgetDataManager.publishCurrentInstalledAppsIfNeeded(in:)`，TreeWidget 并入后直接复用这条管道喂数据，不用另起炉灶。

> 备注：这些文件的精确路径与 SHA 已在本节记录（`AppDelegate.swift` SHA `af60f7a7…`、`ShellTabBarController.swift` SHA `9a5b356c…`）。后续 Spike 若需本地副本，用 GitHub 文件接口单取即可。

### 3.3 内嵌容器 Tab（桥接层，新建）—— ✅ 已落地真实代码

> 2026-11-23 更新：以下伪实现已替换为可编译的真实代码，见 `Sources/` 与
> `scripts/patch_upstream.sh`（自动把适配层挂载进上游树）。

**桥接层**（`Sources/Bridge/`）——把"接管式引擎"变成"可调用库"：
- `LCEngineEntry.h/.m`：对外 API（`bootstrap` / `launchGuestApp` / `installIPA` / `restoreAfterGuestExit`）。
  `launchGuestApp` 内部通过 `dlsym("LiveContainerMain")` 复用上游启动链，
  并显式 `setBool:NO forKey:@"LCOpenSideStore"` 掐死 guest 分支。
  **关键隔离**：swizzle 不在 `+load`/bootstrap 安装，延迟到 guest 启动时才生效，避免污染 openSSS 主循环。

**容器 Tab**（`Sources/Container/`）：
- `ContainerTabViewController.swift`：UIKit 壳，`UIHostingController` 内嵌，`patch_upstream.sh` 自动插入 Shell 第四个 Tab。
- `ContainerRootView.swift`：导入 IPA / 列表 / 启动界面（`UIDocumentPicker` + guest 行）。
- `ContainerViewModel.swift`：状态机，把 SwiftUI 与 C 桥接层连起来。

**深链**（`Sources/Routing/TNBDeepLinkRouter.swift`）：`openssai://` / `livecontainer://` 统一分发，
发通知让 Shell 切到容器 Tab（复用 openSSS 现有的 `NotificationCenter` 观察者模式）。

**关键点**：容器 Tab 的数据源走 `LCEngineEntry`（内嵌 framework），**不依赖 LiveContainer 自己的 AppDelegate**——
这是与上游 `LCAppListView`（依赖 `SharedModel`/`DataManager`）最大的不同，也是"无跳转"成立的前提。

### 3.4 guest 启动与返回（保留但改造）

| 环节 | 现状 | TreeNB 改造 |
|---|---|---|
| 启动 guest | `runApp()` → `invokeAppMain()` | 保留，但入口改为从容器 Tab 触发 |
| 返回主壳 | 悬浮键"杀 guest 重启 LC" | 改为 dismiss 回 openSSS Shell（不重启进程） |
| `LCBootstrap.m:885-908` | guest 出错时 `return 1` 退出 | 改为把错误回传给 openSSS 的 alert（复用 `checkLastLaunchError`） |

### 3.5 小组件（TreeWidget 并入）

- bundle id：`com.kdt.livecontainer.TreeWidget` → `com.openssai.app.TreeWidget`
- 数据快照：`TreeWidgetSnapshotWriter` 改从 openSSS 的 App Group 读写（Keychain service 从 `com.kdt.livecontainer.treeWidget` 改 `com.openssai.app.treeWidget`）
- 深链：`livecontainer://` → `openssai://`（保留 `livecontainer://` 作为兼容别名）
- `@available(iOS 16, *)` 门禁 widget 样式，主工程仍 iOS 15

### 3.6 身份与 plist 归一

| 项 | 取值 |
|---|---|
| Bundle ID | `com.openssai.app`（沿用，证书/数据零迁移） |

## 4. 风险与回退

| 风险 | 说明 | 对策 |
|---|---|---|
| **LC 引擎当作 framework 被 dlopen** | LC 的 `invokeAppMain` 假设自己是主 executable，作为被调 framework 时全局 swizzle（UIApplication/NSBundle.main）可能冲突 | 这是最大风险点。**Spike 阶段必须真机验证**：openSSS 主壳起来后，从容器 Tab 启动一个 guest 能否成功、返回是否稳定 |
| **App Group 合并** | 两个 group 的数据位置不同 | 写一次性迁移：首次启动搬 Keychain 项与配对文件到主 group |
| ~~后台续签~~ | ~~guest 运行时 openSSS 的后台任务不常驻~~ | **已消除**：主壳方案下 openSSS 是主进程，其 `BackgroundServiceManager` / 失败重试逻辑照常运行（见 §2.1 核实） |
| **iOS 版本门槛** | widget iOS16 vs 主工程 iOS15 | `@available` 门禁，或整体升到 iOS16 |

**回退方案**：若 Spike 发现 LC 引擎无法作为被调 framework 工作，退回方案 B——guest 放独立 appex + XPC 通信（见可行性报告 §方案B），成本约翻倍但架构更干净。

## 5. 第一步 Spike（1–2 周，最高优先级）

在任何大规模移植前，先用最小验证回答三个问题：

1. **主壳能起来吗**：openSSS 工程作为主 executable，正常 archive + 侧载，Shell 三 Tab 显示 ✓
2. **引擎能内嵌吗**：把 `LiveContainerShared.framework` 链进 openSSS，dlopen + dlsym 能拿到符号 ✓
3. **guest 能往返吗**：从容器 Tab 启动一个最小 guest App，能全屏运行、悬浮键能返回 Shell ✓

任一失败立即止损，转方案 B。**不要在这三件事验证前写业务代码。**
